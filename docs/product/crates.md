# Rust Chip: product boundary and crate inventory

This is the canonical statement of what Rust Chip is, what each crate in this workspace is, and
how far each one has actually been validated. It was written from reading the code, the manifests,
the tests and the CI workflows, not from crate names or PR titles. A test
(`crates/chip-cli/tests/inventory.rs`) keeps the inventory table below synchronised with the
workspace.

> **Existing code is not automatically product.** A crate earns its place by having a clear
> responsibility, a clear boundary, evidence that it works, and a reason to exist in the current
> product. Everything else is labelled honestly. Compiling is not validation.

For the capability-level view (what the product can do, its gaps and their owners), see
[`capabilities.md`](capabilities.md).

## 1. Product definition

**Rust Chip is an agent runtime that turns model intelligence into bounded, verifiable action.**
It is the agency layer between intelligence and reality.

```text
Goal
  -> Model judgment            (Rust FX, a model behind it)
  -> Bounded proposal          (chip.work-decision.v1, parsed strictly)
  -> Chip validation / authorization
  -> Explicit capability       (declared, with a contract)
  -> Environment -> Execution  (EnvironmentProvider -> WorkEnvironment)
  -> Observation -> Evidence   (generated by Chip from the real operation)
  -> Goal evaluation           (runtime-owned)
  -> Continue / Complete / Recover / Block / Escalate
```

Foundational invariant: **model output is never reality.** It cannot establish an execution, a
receipt, an observation, evidence, success or completion. Those come only from the
runtime/environment/authoritative-observation path. (`AGENTS.md` states the research constitution
behind this.)

**Performance invariant.** Chip must add minimal, bounded overhead around intelligence and
execution. No product-path operation should perform unnecessary model calls, filesystem scans,
subprocesses, serialization, retries, or network requests. It is measured by the baseline in
[`performance.md`](performance.md), which also records where the product does not yet meet it.

Chip owns: accepting work; obtaining model judgment; constraining and validating proposals;
selecting and invoking explicit capabilities; progression, limits, failure handling, recovery,
blocking and escalation; evaluating observed outcomes against the goal; the in-memory runtime
state that loop needs.

Chip does not own: model intelligence, model hosting, provider infrastructure, durable application
state, the computer, arbitrary shell execution, project truth, deployment, package management,
or the human control plane.

## 2. Boundaries

| Responsibility | Owner | What this repository contains |
| --- | --- | --- |
| Model intelligence | Model / provider | nothing |
| Model/provider abstraction | **Rust FX** | `fx-core`, `fx-provider-http` (co-located, versioned independently) |
| Agent agency | **Rust Chip** | `chip-core` and the work path of `chip-cli` |
| Explicit application capabilities | AppPort | nothing. No AppPort code or dependency exists here (audited by `scripts/audit-dependencies.sh`) |
| Computer / execution | **Compute** | `chip-compute` only: a legacy `compute exec` CLI adapter used by demos and proofs. The real `EnvironmentProvider` over Compute lives in the Compute repository (reported by its maintainers; not verifiable from this repository) |
| Project observation / test truth | **PAX** | `chip-pax`: a thin adapter that runs an independently installed `pax` and consumes `pax.execution-result.v1` |
| Durable application authority | FeltDB | nothing |
| Human control plane | Attn | nothing |

Rust Chip may integrate with these systems; it does not absorb their responsibilities.

**Rust FX (this repository) is not the npm/Zig FX.** The Compute-configured distribution ships a
separate agent, Chip/Eve (npm), on a separate FX/Zig stack. Rust FX (`fx-core`, `fx-provider-http`)
and Rust Chip share nothing with them and neither falls back to the other. `fx-core` and
`fx-provider-http` must not depend on `chip-core` or on the npm/Zig stack
(`crates/chip-remote-env/tests/architecture.rs`).

**What Chip requires from FX:** `fx-core`'s `ModelProvider` trait and its request/response types
(`chip-core` and `chip-cli` depend on `fx-core`), and, in `chip-cli` only, `fx-provider-http` to
build a concrete provider. `chip-core` does not depend on `fx-provider-http`. FX is otherwise an
independent product; Chip has no provider-specific logic.

**Environment boundary.** `chip-core` defines `WorkEnvironment`, `EnvironmentProvider`
(`acquire` / `release` / `isolation_capacity`) and `Environments` (which enforces one owning work
per mutable environment). `chip-core` has no dependency on Compute and no Compute type
(enforced by tests and `scripts/audit-dependencies.sh`).
Implementations: `LocalEnvironment` (in `chip-cli`, the default) and `RemoteEnvironment`
(`chip-remote-env`, a generic `exec(argv, env)` transport that names no product). Compute is one
possible provider, supplied by an embedder through `chip_cli::service::serve_in`.

```text
Rust Chip -> EnvironmentProvider -> Environment   (local machine | remote via exec transport | Compute, by an embedder)
```

## 3. Classifications

| Class | Meaning |
| --- | --- |
| PRODUCT | Required or user-facing Rust Chip (or Rust FX) functionality: clear responsibility, stable boundary, meaningful tests, a reason to exist independently |
| SUPPORTING | Required implementation infrastructure that is not itself a product concept (none at present) |
| INTEGRATION | A thin adapter to an external system |
| EXPERIMENT | Research that informed the architecture but has not earned a role in the product |
| PROOF | Code or fixtures created to establish a claim or milestone |
| DEPRECATED | A previously used direction that has been replaced |
| UNPROVEN | Code that exists but lacks validation for product status (none is solely UNPROVEN; see section 8) |

**Disposition**: `KEEP` (maintained), `FROZEN` (kept as research or compatibility; not extended
without a justification under `AGENTS.md` section 14), `REJECTED` (a negative result; kept only as
a record). PRODUCT, SUPPORTING and INTEGRATION crates are `KEEP` or `FROZEN`; every other class
is `FROZEN` or `REJECTED`.

**Validation levels**

| Level | Meaning |
| --- | --- |
| L0 | Compiles |
| L1 | Unit tested |
| L2 | Integration tested (including against mocks and test doubles) |
| L3 | Tested against a real external dependency (real `pax`, `git`, filesystem, HTTP endpoint) |
| L4 | A real end-to-end workflow tested |
| L5 | Production / distribution path validated |

Two columns, because they are different claims:

* **CI level**: what `cargo test --workspace` and the default CI jobs reproducibly establish. Where a
  test needs PAX it passes by returning early when PAX is absent, so L3 applies only where PAX is
  installed. CI installs PAX v0.4.1 pinned by commit (`674f3b3`).
* **Reported level**: a higher level shown by a run that is not part of default CI (a manual
  workflow, a live-model run recorded in `AGENTS.md`, or work in another repository). It is a
  report, not something this repository reproduces. `-` means none is recorded.

## 5. Crate details

Test counts are from one run of `cargo test -p <crate>` (section 7). "Ships" means linked into the
`chip` release binary (`scripts/package-release.sh` builds `cargo build --release -p chip-cli`
with default features, so `chip-local-ml` and `chip-laya-reasoner` are not linked).
"Default runtime" means used by `chip work`, `chip serve` or `chip verify`.

### Product

**`chip-core`** (PRODUCT, L2). *Problem:* the model/runtime authority boundary. *Contents:* the
capability model and invocation validation, `ModelDecisionBoundary` (strict
`chip.work-decision.v1`, no repair), executors/observations/evidence, the bounded work loop
(`run_work`, `WorkLimits`, terminal states, `WorkEvent`s, `GoalEvaluated`), the safety auditor, and
the environment contract. *Authority:* Chip's. *Deps:* `fx-core` only. *Ships:* yes. *Default
runtime:* yes. *Tests:* 267, including architecture tests that forbid Compute, FeltDB and AppPort
dependencies and pin invocation-boundary behaviour. *Real dependency:* none by itself; its
real-execution evidence is through `chip-compute` (PR36-38, see section 6). *Contains non-product
surface, audited:*

* `reasoning.rs` (`LocalReasoner`, `ReasoningInput`, `TestLocalReasoner`): the seam the
  local-reasoner experiments plug into, and a **test double**. The product installs no reasoner:
  `chip work`, `chip verify` and `chip serve` never call `with_local_reasoner`. With none installed,
  a locally proposed request that has no valid evidence escalates to the model (tested in
  `chip-core/tests/work_loop.rs`), which is the same fail-closed behaviour the double gave. In the
  product configuration that branch is not even reachable: the product's local policy only ever
  proposes `Complete` or nothing, and every product capability is evidence-reuse-prohibited, so a
  proposed request is executed, not assessed. `TestLocalReasoner` stays for tests, for the reference
  baseline the experiments are measured against, and for `chip-cli`'s proof and benchmark commands.
  `crates/chip-cli/tests/product_path.rs` keeps it out of the product modules.
* `decision_state.rs` (`CapabilityDecisionState`, `GraphStateToken`, `ImpactState`): **experimental
  residue.** Nothing in `Agent` or `run_work` reads it; only the experiment crates and `chip-cli`'s
  research commands do. Kept because those crates and their golden files depend on the encoding. A
  test pins that the work loop does not use it. (`chip-graph` defines a separate `GraphStateToken`.)
* Escalation-context policies (`EscalationContextPolicy`, `FullEscalationContext`,
  `DeduplicatedEscalationContext`): **product.** Deciding what the model is told at an escalation is
  part of the agency loop, and both policies are used: `chip work` uses the deduplicating one,
  `chip verify` the full one. The trait is small and has two product implementations, so it stays.
  Their origin in the local-decision research does not make them research code.
* The evidence store and `assess_evidence` (PR11-13): the store is used for recorded evidence and the
  audit; the reuse/assess path is exercised by tests and proof commands, and by no product command.

**`chip-cli`** (PRODUCT, L3). *Problem:* the one executable, `chip`, and the library an embedder
uses (`service::serve_in`). The product surface is `chip work`, `chip serve`, `chip verify`,
`chip capability-exec` and `chip --version`, implemented in `software_work.rs`, `service.rs`,
`verify.rs`, `local_environment.rs` and `provider_selection.rs`. *Ships:* yes. *Deps:* see
section 5.1. *Tests:* 302, including black-box runs of the real `chip` binary against a mock model
endpoint, real PAX, real `git` and the real filesystem, and a packaged smoke test in CI.
*Not product, same binary:* every other subcommand and module (section 5.1).

**`chip-project`** (PRODUCT, L3). *Problem:* the software-work capabilities `project.list`,
`project.search`, `project.read`, `project.write`, and the four read-only `project.git.*`
observations. Path rules, size bounds, atomic writes with read-back and fixed git argv are all
Chip-owned. *Boundary:* an environment capability implemented by Chip; it is not PAX's job (PAX
observes test results) and PAX does not read or write project files. *Deps:* `chip-core`. *Tests:*
51; real filesystem and real `git`. *Default runtime:* yes. *Not claimed:* sandboxing. Git itself runs
repository-configured filters (stated in `git.rs`); the model's writes plus `pax.test` are code
execution through the project's own tooling.

**`fx-core`** (PRODUCT, Rust FX, L2). The provider-neutral model boundary (`ModelProvider`,
request/response, `Secret`, `FxError`). 7 tests. Independent of Chip (no dependency on any other
workspace crate). Reported L4 means it was in the path of the live PR36-38 runs.

### Integration

**`fx-provider-http`** (INTEGRATION, Rust FX). One HTTP provider with three wire adapters:
`openai-compatible`, `anthropic`, `ollama`. 41 tests, all against a local mock HTTP server except
`live_provider.rs`, which runs only when `FX_PROVIDER_*` variables are set and otherwise returns.
Provider matrix in section 5.3.

**`chip-pax`** (INTEGRATION, L3). Runs an independently installed `pax` (verified as PAX >= 0.3.0 and not
the POSIX `pax` archiver; lazily: located without starting a process, verified once per executor
when first needed), fixes `pax --dir <root> --json test`, parses stdout strictly as
`pax.execution-result.v1`; and provides `project.observe` (PAX >= 0.4.1), a bounded `pax --json observe`
whose `pax.observation.v1` document is parsed strictly and rendered compactly by Chip, with the scope grammar
and project-root containment checked before PAX runs. Chip consumes PAX's `status`; it does not embed or reimplement PAX.
35 tests (plus `chip-cli/tests/pax_probes.rs`, which counts the PAX processes `chip work` starts); the real-PAX ones run only where PAX is installed (CI installs it). *What this proves:*
Chip can run PAX, reject malformed or mismatched results, and treat PAX `passed` as the test
authority. *What it does not prove:* PAX behaviour on projects or toolchains beyond those the tests
build, or anything about PAX versions other than 0.3.0.

**`chip-remote-env`** (INTEGRATION, L3). A generic transport (`CommandRunner`: `exec(argv, env)`,
no stdin) plus `RemoteEnvironment`/`RemoteCapabilityBackend`, which asks the far side to run
`chip capability-exec`. It names no product. 8 tests; the CI level comes from an in-process local
runner driving real git and real PAX, which is not a remote environment. The reported L4 is the
Compute-side real session/job tests and concurrent-isolation tests the maintainers report from the
Compute repository.

**`chip-compute`** (INTEGRATION, FROZEN, L2). Legacy adapter: `ComputeExecutor` runs
`compute exec <entrypoint> --runtime <rt> --json` and translates the result. It is **not** an
`EnvironmentProvider`, is not in the work/serve path, and is used by the demo, benchmark and horizon
code in `chip-cli`. 50 tests; those that need a real `compute` binary report `SKIPPED` and pass when
it is absent. Reported L4: the PR36-38 live runs in `AGENTS.md` used it. The `live-compute.yml`
workflow is manual only. It stays because the PR36-39 experiments depend on it.

### Experiments and proof

None of these is used by `chip work`, `chip serve` or `chip verify`. Several are linked into the
shipped `chip` binary only because `chip-cli` also hosts their commands (section 8).

* **`chip-local-decision`, `chip-local-decision-train`** (EXPERIMENT, REJECTED): *the tiny-ML negative
  experiment.* A 129-parameter linear classifier over a canonical decision state, with its trainer
  and shipped parameter files. **Explored whether a tiny local model could improve deterministic
  decision behavior. It did not earn a role in the production architecture.** On the 376 unseen cases
  of the PR25 corpus it added 0 safe local decisions beyond the deterministic baseline and made 1
  false continue (`crates/chip-local-decision/models/local-decision-pr25.report.txt`). The
  deterministic policy in the same crate is the baseline it was compared with and is not used by the
  runtime either. The trainer is dev-only and nothing depends on it. Kept as a record.
* **`chip-decision-corpus`** (EXPERIMENT): the versioned generator and checked-in corpus for that
  experiment, plus a second Rust binary (`chip-decision-corpus verify`, run in CI). Not shipped as a
  product executable.
* **`chip-wasm-decision`, `chip-wasm-decision-host`** (EXPERIMENT): a `no_std` Wasm module that
  makes the same continue/escalate judgment and a fuel-bounded `wasmi` host. Built green for
  `wasm32-unknown-unknown`; deterministic and tested against a native oracle. Deterministic
  verification infrastructure and a benchmark for the experiment, not a production runtime
  component. `chip-wasm-decision` has no tests of its own (exercised through the host crate).
* **`chip-wasm-reasoner`** (EXPERIMENT): an earlier, separate Wasm `LocalReasoner` host (ABI v1).
  Overlaps in purpose with the two crates above; kept because the corpus evaluation and benchmarks
  still use it. Candidate for removal if those are retired.
* **`chip-local-ml`, `chip-laya-reasoner`** (EXPERIMENT): two optional adapters that ask a local
  model (via `rust-ml-runtime`, or native `laya-decision`/candle) one continue/escalate question.
  Feature-gated, off by default, optional CI workflows (`local-ml.yml`, `laya.yml`) outside normal PR
  validation. Their unit tests use test doubles or a random-weight checkpoint whose verdicts "mean
  nothing" (`chip-laya-reasoner`'s own words). No result with a real model is recorded here. They
  overlap with each other and with the rejected experiment.
* **`chip-reasoning-corpus`** (PROOF): the corpus and replay harness that defines what a
  `LocalReasoner` is responsible for. Fixture for the above.
* **`chip-graph`** (EXPERIMENT, L1): a deterministic architecture graph of a Rust repository
  (`chip init`, `chip graph`, `chip slice`, `chip impact`). Well covered by golden tests, but no
  product component consumes it. Project *structure* is observation that belongs with PAX or the
  environment rather than in the agency loop; "which part of the project is relevant" is not
  observation at all (in this crate it is declared by an external catalog, elsewhere it is
  interpretation), see
  [`project-observation-boundary.md`](project-observation-boundary.md). Kept because it fed the
  decision-state design; extending it needs a justification under `AGENTS.md` section 14.

### 5.2 `chip serve`

**PRODUCT, as a local trusted-client interface only.** It is the supported way to embed Chip
(`serve_in` with a custom `EnvironmentProvider`) and is exercised by the packaged smoke test.
Implemented and tested: `POST /v1/work` (goal only; every other field is rejected),
`GET /v1/work/{id}`, `GET /v1/work/{id}/events`, `POST /v1/work/{id}/cancel`, `GET /v1/metrics`,
`GET /health`; a FIFO queue with a concurrency limit and a queue bound (429 when full); one
environment acquired per work and released at the end; panic containment per work. Behaviour to
know: events are available only when a work ends; cancelling running work is advisory (the in-flight
call is not interrupted); work state is in memory only and a restart forgets it; no authentication,
no CORS, loopback by default, so it is not for remote or multi-user use; the local machine is one
mutable directory, so the standalone service runs one work at a time. Isolation between concurrent
works exists only for providers that supply isolated environments; none is provided in this
repository. Level L3 (real PAX, real binary over HTTP, mock model).

## 6. What the research established and where it lives

`AGENTS.md` section 7 records the live results of PR36 (invocation boundary), PR37 (zero-overlap
selection) and PR38 (wrong-judgment recovery). The code that backs them in this repository is the
`chip-core` tests (`invocation_boundary.rs`, `capability_selection.rs`, `protocol_contract.rs`), the
`chip-compute` tests (`goal_recovery.rs`) and `chip-cli`'s `horizon.rs` (PR39). The live model runs
themselves are not reproduced by default CI and their raw outputs are not stored in this repository.
These are PROOF artifacts for the thesis. They are not product surface and do not by themselves
make `chip-cli`'s `--test-*` commands product. Capability selection as *product* is the smallest
mechanism that enforces "a model may invoke only an explicitly authorized capability according to
its contract": capability declaration, `validate_inputs`, and `ModelDecisionBoundary`, all in
`chip-core`/`chip-project`/`chip-pax`. The semantic, opaque, permutation and zero-overlap
experiments only measure model robustness against that mechanism.

## 8. Not yet proven

* **No real-model run of `chip work`/`serve`/`verify`.** Their tests use a mock model endpoint; the
  opt-in real-model tests (`CHIP_TEST_REAL_MODEL=1`) are not run in CI and no result is recorded.
  Hence `chip-cli` is L3, not L4. PR36-38 were live but on a Compute-backed workload, not on this path.
* **Provider combinations** beyond the matrix above; Ollama and vLLM against a real server.
* **Distribution:** no evidence that a tagged release has been published and consumed; one target;
  no signing; the smoke test uses a stand-in model and, without PAX, an identity-only PAX.
* **Experiment code ships in the binary.** `chip-cli` links the graph, decision, Wasm and Compute
  crates unconditionally, so the product binary carries unproven code and subcommands. Making them
  opt-in features is a follow-up and was deliberately not done here, because it changes the CLI.
* **`TestLocalReasoner` left the production path** (previously `chip work` and `chip verify` installed
  it; it was never consulted, see section 5). It remains a documented test double. The proof and
  benchmark commands of `chip-cli` still use it and are linked into the same binary.
* **Product code still calls one proof module.** `software_work.rs` and `verify.rs` render the
  canonical measurement through `work_demo::measurement_json`, which lives in the demo module. It is
  pinned as the only such coupling (`crates/chip-cli/tests/product_path.rs`); moving it is a
  follow-up. (`verify`'s local policy `ReactToObservation` and the reply recorder `Recording` used
  to be imported from the `--test-pax-work` and PR39 proof modules and now live in `verify.rs`.)
* **Tolerated Markdown fence.** `ModelDecisionBoundary` accepts one code fence around the whole reply.
  It is documented and tested but is a narrow exception to "no repair" (`AGENTS.md` Invariant 6).
* **Isolation:** concurrent isolated environments are not demonstrated in this repository; the
  local environment is deliberately single-owner and the remote one is only tested in-process. Secrets
  and host paths: PAX diagnostics shown to the model can contain host paths (stated in the README).
  No sandbox is claimed.
* **Service:** no persistence, authentication, streaming events or remote exposure; cancellation of
  an in-flight call is advisory.
* **Mock-only integrations:** `chip-compute` without a `compute` binary, `fx-provider-http` against
  any real endpoint, the Laya/local-ml adapters against real models.
* **Skips look like passes.** Tests that say `SKIPPED` return successfully. A green run on a machine
  without PAX, Compute, Git or a model proves less than the same run elsewhere.
* **Duplicate experiments.** `chip-wasm-reasoner` vs the `chip-wasm-decision` pair, and
  `chip-local-ml` vs `chip-laya-reasoner`, answer the same question twice with no recorded result.
  Both pairs are candidates for removal once nobody needs the benchmark commands.
* **No product owner** for the experiment crates; they are `FROZEN` so that is explicit.

## 9. Supported surfaces

`chip work`, `chip verify`, `chip serve` (local trusted clients), `chip capability-exec` (used by
`chip-remote-env`), `chip --version`, and the embedding API `chip_cli::service::serve_in` with an
`EnvironmentProvider`. Capabilities: `project.list`, `project.search`, `project.read`,
`project.write`, `project.git.status|diff|diff_stat|log`, `pax.test`.

## 10. Explicit exclusions

No shell, command or process capability; no model discovery, fallback, routing or retries; no
planner, hidden memory or persistent agent memory; no AppPort, FeltDB or Attn integration; no
Compute client in `chip-core`, the Rust FX crates or `chip-remote-env`; no embedding of PAX; no
durable work state; no remote or authenticated serving. Experiments listed above are not product
features and do not become product by being built.

`crates/chip-cli/benches/baseline.rs` is the performance baseline harness (a bench target, not shipped, not a test); see [`performance.md`](performance.md).

## 11. Workspace hygiene done in this audit

Removed `examples/single_turn.rs` (outside any package, never built, referenced nowhere) and the
unused `tokio` dev-dependency of `chip-remote-env`. Every workspace crate has a purpose (product,
integration, experiment or proof), so none was removed. No crate was renamed, merged or moved, and
no abstraction was added.

## 12. Product reasoning boundary

`chip work`, `chip verify` and `chip serve` install no local reasoner. Their runtime-owned decisions
are: the local policy (`CompleteWhenVerified` for work; `ReactToObservation` for verify, which asks
the model first), the strict model decision (`ModelDecisionBoundary`), capability and invocation
validation, goal evaluation from authoritative observations (a completion is refused until the
goal's observation holds), the work limits, and, for any locally proposed request without valid
evidence, escalation to the model. `crates/chip-cli/tests/product_path.rs` pins that the product
modules name no reasoner, use only product crates and product modules, and construct their `Agent`
without one; the same file pins that the work loop does not read `decision_state.rs`.
